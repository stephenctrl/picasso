# GPU access and performance TODO

This is a profiling-gated implementation plan, not a claim that Picasso currently implements WebGPU or WebGL. No new GPU API, dependency, or runtime feature is added by this document.

## Current architecture and boundaries

- The editor in [`src/pages/editor/EditorPage.tsx`](src/pages/editor/EditorPage.tsx) renders React DOM layers, not a GPU canvas editor. [`src/render.ts`](src/render.ts) shares absolute-positioned `div`/`p`/`button` styles with HTML/CSS generation; [`src/components/ProjectPreview.tsx`](src/components/ProjectPreview.tsx) scales the same DOM representation.
- The browser compositor and Canvas2D **may already use hardware acceleration**. Actual use depends on browser, driver, device, rendering operation, and browser policy; CSS transforms or a `2d` context do not prove GPU execution. React reconciliation, JavaScript layout calculations, HTML parsing/style/layout, and JSON/HTML/SVG string serialization are CPU work, not automatically offloaded by enabling WebGPU. [1][2][3]
- [`src/export.ts`](src/export.ts) builds SVG strings and uses Canvas2D text measurement. [`src/aiImage.ts`](src/aiImage.ts) decodes design SVG/reference images, draws a white-backed Canvas2D image, and synchronously encodes JPEG with `toDataURL`: maximum 1600px edge and 2 MiB output; reference inputs are PNG/JPEG/WebP up to 5 MiB.
- [`src/importHtml.ts`](src/importHtml.ts) sanitizes markup, measures static HTML/CSS in a sandboxed iframe, and flattens it to editable layers. Its cached 1×1 color readbacks deliberately use `willReadFrequently`; this is a readback/software-rendering tradeoff, not a GPU candidate by default. [`src/layout.ts`](src/layout.ts) performs CPU alignment, arrangement, and snap calculations. Keep import sanitization, CSP, and resource blocking intact. [3]
- Keep the [release contract](docs/requirements.md): at most **200 committed layers**; the same committed `Project` supplies Code, Preview, JSON, HTML, SVG, and AI snapshots. Do not export transient gesture visuals or unaccepted AI proposals. Preserve one undo action per completed gesture, cancellation restoring the original, keyboard/text editing, and explicit save/AI behavior.

## 1. Measure before choosing an accelerator

- [ ] **Record a reproducible production baseline first.** Use the existing production build/server path, fixed project fixtures at 0/50/200 layers (199→200 for Add), fixed viewport/zoom/DPR, and identical interactions: add, select, undo/redo, drag/resize, zoom, text edit, Code/Preview switch, HTML import, export, and AI image preparation without provider timing. Record browser/OS/device, power mode, warmup, sample count, and median/p95. Capture Performance traces separating input delay, handler/React CPU, style/layout, paint, compositing, long tasks, and missed frames; use paint flashing/layer inspection to identify repaint regions. A double-`requestAnimationFrame` timer is only a responsiveness proxy, not proof of screen presentation or GPU completion. **Acceptance:** a saved before/after protocol and traces identify the dominant cost for each slow interaction. [1][2]
- [ ] **Set and apply benchmark gates before implementation.** Choose the targeted bottleneck from those traces; eliminate redundant CPU/render/serialization work before adding shaders. Proposed rollout gate: repeatable ≥20% improvement in the targeted p95 cost, no >5% p95 regression in other core interactions beyond measured noise, and no correctness/accessibility regression. For continuous manipulation, target the display's frame budget (16.7ms at 60Hz; 8.3ms at 120Hz), reporting missed-frame rate rather than promising universal frame rates. **Acceptance:** repeated same-device production runs meet agreed gates; otherwise keep the simpler path and document the result.

## 2. Prefer the existing compositor path

- [ ] **After paint/layout profiling, evaluate bounded `transform`/`opacity` animation for UI feedback or temporary manipulation visuals.** Avoid animating layout properties or `transition: all`; do not smooth pointer movement by making artwork trail the pointer. Apply `will-change` only to a measured hot element, only around its activity, and remove it afterward. Never apply `translateZ(0)` or permanent promotion to all 200 layers: layer textures consume memory and promotion may change stacking/rasterization. **Acceptance:** traces show less paint/layout or fewer missed frames without unbounded layer/memory growth. [2]
- [ ] **Check visual and interaction parity before retaining promotion.** Keep document coordinates authoritative; align artwork, snap guides, selection outlines, resize hit regions, and direct-text overlays at every supported zoom and high DPI. Inspect crisp text at fractional scales; scaling cached raster text can blur it, and scaling is not a replacement for real text reflow during resize. Preserve focus rings, native controls, screen-reader labels, and keyboard actions. Disable nonessential motion under `prefers-reduced-motion`. **Acceptance:** pointer/keyboard hit targets and final geometry match the unanimated path, with no accessibility or reduced-motion regression.

## 3. Optional worker rasterization, only if image preparation blocks input

- [ ] **Prototype a dedicated Worker + OffscreenCanvas path for `aiImage.ts`, not the editor surface.** Prerequisite: traces show meaningful decode/draw/JPEG main-thread blocking. Detect Worker, OffscreenCanvas 2D, image decoding, and blob encoding support in the actual worker; verify SVG decoding and font availability separately from PNG/JPEG/WebP. Workers run CPU JavaScript on another thread; they are **not inherently GPU execution**, and OffscreenCanvas2D acceleration is not guaranteed. Retain the existing main-thread Canvas2D path as the CPU-capable compatibility fallback when worker facilities or a format are unsupported. [3][4]
- [ ] **Preserve the image contract and lifecycle.** Keep current file validation, dimensions, white background, JPEG quality/size limits, and committed-project source. Preserve main-thread `projectSvg` text measurement unless worker font/measurement parity is established. Use operation/revision IDs and cancellation messages; ignore stale results after abort, project replacement, or a newer request. Terminate work or release resources when cancelled/disposed, close ImageBitmaps, and revoke object URLs. Measure message/structured-clone or transfer costs, decode, rasterization, encoding/readback, and final base64 conversion—not just drawing time. **Acceptance:** cancellation never sends stale images, unsupported browsers still work, output dimensions/appearance/limits match, resources are released, and end-to-end latency/input responsiveness clears section 1's gate. JPEG bytes need not be identical across browser encoders.

## 4. Explicit GPU APIs are a later, isolated decision

- [ ] **Require a demonstrated pixel-parallel workload before a WebGPU experiment.** Current 200-layer DOM geometry, HTML import parsing/layout, and string exports do not justify building a replacement GPU canvas editor. Consider only a measured raster/image operation whose benefit survives texture upload, pipeline setup, GPU→CPU readback, JPEG encoding, and base64 costs. Keep data on the GPU where practical, but account for the eventual CPU/network output. **Acceptance:** a short comparison against Canvas2D/worker CPU execution meets the benchmark gate, including cold initialization and memory costs. [5][6]
- [ ] **If justified, design asynchronous, fail-open access.** Check `isSecureContext` and `navigator.gpu`; asynchronously call `requestAdapter`, handle a null adapter, inspect its supported features/limits, and request only required capabilities with `requestDevice`. Catch initialization/validation failures; handle `device.lost`, stop pending work, release resources, and fall back without losing the project. Recreating a device requires recreating its resources. Default/low-power selection is preferable unless evidence justifies higher power; preference is a hint, not control over a specific GPU, and an adapter can be software-backed. **Acceptance:** missing API, no adapter, inadequate limits/features, request failure, and device loss all leave local editing/export usable. [5][6][7]
- [ ] **Check deployment eligibility, not hardware flags.** Picasso's Express server binds to `127.0.0.1` and serves HTTP locally. Loopback/localhost origins are generally potentially trustworthy, but actual secure-context treatment and WebGPU availability depend on the browser/environment: detect both at runtime. Secure context alone does not guarantee an adapter. Do not require users to change browser flags, disable security, or force a hardware adapter. Any future non-loopback deployment needs a separate HTTPS/security design, not a change to this local-only server. [8]
- [ ] **Evaluate WebGL2 only as an alternative for the same proven raster workload.** Detect a non-null `webgl2` context, query necessary capabilities outside hot loops, handle context loss/restoration and allocation failure, release textures/buffers, and retain the non-GPU path. Do not add a second renderer merely because WebGPU is unavailable. **Acceptance:** benefit exceeds maintenance/setup/readback costs, including software-renderer behavior; simulated context loss leaves the project intact. [3][9]

## 5. Compatibility and rollout checklist

- [ ] **Run the same production protocol across representative configurations:** integrated and discrete GPUs; hardware and available software adapters; API unsupported/disabled/no-adapter cases; Chrome/Edge, Firefox, and Safari where available; standard and high DPI, fractional zoom, 200-layer text-heavy and overlap-heavy projects, maximum-size artboards/references, AC/battery/low-power modes, and reduced motion. Record actual capabilities, not assumptions from browser names. Include cold/warm runs, repeated cancellation, device/context loss, keyboard-only use, text input, and screen-reader checks. **Acceptance:** section 1 gates hold on intended targets; unsupported/slow paths remain functional with no required GPU.
- [ ] **Protect output and behavior before broad rollout.** Compare JSON/HTML/SVG from the same committed `Project` before/after; keep deterministic serialization and existing text-measurement behavior in a controlled browser/font environment. Do not replace vector/HTML exports with framebuffer screenshots or promise identical typography across OS fonts. Confirm preview/AI preparation does not mutate the source, gestures undo/cancel correctly, and saving/live AI do not become automatic. Track peak memory, readback/copy overhead, and battery impact as well as FPS; reject acceleration that wins shader time but loses end-to-end latency or power.

## AI is a separate boundary

`/api/suggest` in [`server/index.ts`](server/index.ts) forwards to the configured remote provider via [`server/ai.ts`](server/ai.ts). Browser GPU access cannot control or accelerate that provider's GPU inference or network latency. Local browser/server GPU AI would require a separate product/security design, model/runtime selection, downloads/licensing, memory budgets, inference quality, and offline/privacy evaluation; it is not an optimization of the existing remote request. Keep credentials server-side and AI optional and explicitly accepted.

1. [Chrome DevTools: Analyze runtime performance](https://developer.chrome.com/docs/devtools/performance) — main-thread traces, layout, frames, and bottleneck attribution.
2. [Chrome/web.dev: High-performance CSS animations](https://web.dev/articles/animations-guide) — transform/opacity, paint inspection, and selective layer promotion.
3. [MDN: HTMLCanvasElement.getContext](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/getContext) — context detection and the Canvas2D `willReadFrequently` software/readback tradeoff.
4. [MDN: OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas) — worker rendering, transferable ownership, blob encoding, and context loss.
5. [MDN: WebGPU API](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API) and [W3C WebGPU specification](https://www.w3.org/TR/webgpu/) — explicit rendering/compute resources, devices, features, and limits.
6. [MDN: GPU.requestAdapter](https://developer.mozilla.org/en-US/docs/Web/API/GPU/requestAdapter) — asynchronous detection, null/fallback adapters, and power preferences.
7. [MDN: GPUDevice.lost](https://developer.mozilla.org/en-US/docs/Web/API/GPUDevice/lost) — device-loss lifecycle and resource recreation.
8. [MDN: Secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts) — trustworthy loopback origins and runtime detection.
9. [MDN: WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices) — memory budgets, context loss, and blocking readback costs.
